STM32L476RG · Cortex-M4F ESP32 · ESP-IDF v6 Bare-metal + FreeRTOS Both firmwares build clean

Ultra-Low-Power Dual-MCU IoT Telemetry Node

A two-chip sensor node: an STM32L4 spends >99% of its life in STOP2 deep sleep sampling battery/temperature/ADC channels via DMA, wakes an ESP32 over UART only when a batch of samples is ready, and the ESP32 publishes that telemetry to an MQTT broker over Wi-Fi. This page documents the actual, currently-compiling source code — architecture, every function's role, register-level configuration, protocol framing, and the full call/data flow between layers.

1. Project Overview

This repository is firmware for a two-MCU sensor node designed around one constraint: minimize average current draw. The STM32 side never needs a general-purpose OS or connectivity stack — it is bare-metal C directly programming CMSIS registers. The ESP32 side needs Wi-Fi and TCP/MQTT, which is realistically only practical on top of ESP-IDF's FreeRTOS-based stack, so it runs two FreeRTOS tasks connected by a queue. The two chips talk over a single UART link using a small framed binary protocol defined once, in common/protocol_spec.h, and compiled into both firmwares.

MCURoleLanguage / runtimePower posture
STM32L476RGSensing + power managementBare-metal C, CMSIS registers, no OS>99% time in STOP2 (deep sleep, SRAM retained)
ESP32 (ESP-WROOM-32)Connectivity gatewayC++ on ESP-IDF / FreeRTOSIdle/light-sleep between UART bursts (Wi-Fi power-save managed by ESP-IDF)

Both firmware trees in this repository are real, currently-compiling builds, not illustrative pseudocode — see §11 for the actual toolchain output. Every register name, pin assignment and function signature described below is copied from the live source tree, not paraphrased.

2. Hardware & System Block Diagram

Sensors feed the STM32's ADC; ADC conversions land directly in SRAM via DMA with zero CPU involvement. Once a full circular-buffer lap completes, the STM32 wakes, averages the samples, and bursts one telemetry frame to the ESP32 over UART. The ESP32 validates the frame, ACKs it, queues it internally, and a second task publishes it to an MQTT broker over Wi-Fi.

Fig. 1 — System block diagram: sensing/DMA pipeline (left) to Wi-Fi/MQTT gateway (right), connected over a single UART link.

3. Layered Software Architecture

Both firmware trees follow the same layering discipline, mapped here onto MCAL / BSW(Service) / Application terminology so the responsibilities read the same regardless of which MCU you're looking at:

LayerSTM32 directoryESP32 directoryResponsibility
MCALdrivers/components/uart_receiver/ (driver half)Direct register/peripheral-driver access. Knows about hardware, nothing about the telemetry protocol.
BSW / Servicemiddleware/components/uart_receiver/ (parser half), components/wifi_mqtt_client/Protocol framing, CRC, state machines, connectivity service. Bridges hardware to business logic.

Fig. 2 — Layer stack per MCU. Arrows show the calling direction: Application calls into BSW, BSW calls into MCAL. Lower layers never call upward.

On the ESP32 side the uart_receiver component straddles MCAL+BSW: it owns both the raw driver/uart.h calls (MCAL-ish) and the byte-level frame parser/CRC state machine (BSW-ish) in a single file, because ESP-IDF's component granularity doesn't force a further split. It's called out here rather than hidden, since the STM32 side keeps the equivalent split as two separate files (drivers/dma_adc.c vs middleware/uart_handshake.c).

6. STM32 Firmware Deep Dive

6.1 Application entry point — app/src/main.c

Fig. 4 — main() control flow. Every box names the real function called, in call order.

There is intentionally no retry/backoff logic: if uart_send_telemetry_and_wait_ack() returns false, the code sets a comm-error status bit on the (already-local, about-to-be-discarded) payload and moves on — the next DMA-complete cycle produces a fresh sample set and tries again, so a dropped frame is superseded rather than resent.

6.2 Power & clock driver — drivers/src/power_manager.c MCAL

Fig. 5 — STM32 power state machine. Only one wakeup source is armed: DMA1_Channel1_IRQn (via dma_adc_init()'s NVIC_EnableIRQ).
FunctionRegisters touchedWhat it does
pm_init()RCC->APB1ENR1 |= RCC_APB1ENR1_PWRENClocks the PWR peripheral — without this, every later PWR->* write is a no-op.
pm_configure_unused_gpios_analog()RCC->AHB2ENR (GPIOAEN), GPIOA->MODERSets all of GPIOA to Analog mode (kills input-buffer leakage current), then re-opens exactly WAKE_PIN (output) and the two USART2 pins (alt-function) via board_config.h's pin numbers.
pm_disable_unused_clocks()—Documented no-op today (unused peripherals reset with their clocks already off) — the designated place to gate a future driver's clock if it's later added and unused.
pm_enter_stop_mode()PWR->SCR (CWUF), PWR->CR1 (LPMS=STOP2), SCB->SCR (SLEEPDEEP)Clears stale wake flags, selects STOP2, arms deep-sleep, executes __WFI(). Execution resumes on the next line after the DMA IRQ.
pm_enter_sleep_mode()SCB->SCRPlain SLEEP (peripherals stay clocked); declared in the header, not currently called by main.c.

6.4 UART handshake middleware — middleware/src/uart_handshake.c BSW

FunctionKey registersWhat it does
uart_handshake_init()RCC->APB1ENR1 (USART2EN), GPIOA->AFR[0], USART2->BRR, USART2->CR1 (TE, RE, UE)AF7-maps PA2/PA3 to USART2, sets BRR = SystemCoreClock / 115200 (16× oversampling default), enables TX/RX/peripheral. 8N1 is already the CR1/CR2 reset default.
uart_wake_esp32()GPIOA->BSRR10ms pulse on WAKE_PIN (atomic set then reset via BSRR), then a 100ms settle delay for the ESP32 to finish waking and bring its UART up.
uart_wait_for_byte() (static)USART2->ISR (RXNE), USART2->RDRPolls for one specific byte with a loop-count timeout (not calibrated to real time — the caller only needs "did an ACK show up at all").
uart_send_buffer() (static)USART2->ISR (TXE, TC), USART2->TDRBlocking byte-at-a-time transmit; waits for TC after the last byte so the caller can assume the wire is idle on return.
uart_send_telemetry_and_wait_ack()—Builds the uart_frame_t (sync bytes, length, payload, CRC16), sends it, and blocks up to ~100000 poll iterations waiting for PROTOCOL_ACK_BYTE.

6.5 Millisecond delay — drivers/src/systick_delay.c MCAL

systick_delay_init() loads SysTick->LOAD = SystemCoreClock/1000 - 1 and enables the counter with the processor clock as source, no interrupt. delay_ms(ms) busy-polls SysTick_CTRL_COUNTFLAG_Msk once per requested millisecond — simple and sufficient for the two call sites (uart_wake_esp32()'s 10ms/100ms pulses).

7. ESP32 Firmware Deep Dive

7.1 Application entry point — main/main.cpp

app_main() creates a QueueHandle_t sized for 10 telemetry_payload_t structs, calls uart_receiver_init(queue) and wifi_mqtt_init(), spawns uart_rx_task (priority 5, 4096-byte stack) and mqtt_pub_task (priority 4, 4096-byte stack, handed the queue as its pvParameters), then idles in a vTaskDelay(10s) loop — the two tasks do all the real work.

7.2 UART receiver — components/uart_receiver/uart_receiver.cpp BSW + MCAL

The heart of this component is a 7-state byte-at-a-time parser. This is a real state machine in the code (a C++ enum switched on per byte), not a metaphor:

Fig. 6 — uart_receiver_task's frame parser state machine, drawn directly from the switch(state) in the source. Solid arrows: normal advance. Dashed: resync/reject paths.
FunctionWhat it does
uart_receiver_init(queue)Stores the output queue handle, configures UART1 (115200 8N1, no flow control) via uart_driver_install/uart_param_config/uart_set_pin (TXD=GPIO17, RXD=GPIO16).
uart_receiver_task(void*)Infinite loop: uart_read_bytes() with a 20-tick timeout, feed each byte through the state machine above. On STATE_CRC_H, recomputes calculate_crc16() over the received payload and compares to the received CRC.
send_response(byte) (static)uart_write_bytes() of a single ACK (0x06) or NACK (0x15) byte back to the STM32.

On CRC match: logs, ACKs, xQueueSend(out_queue, &payload_buf, portMAX_DELAY). On mismatch: logs the calculated vs. received CRC and NACKs — the STM32 side does not retry on NACK (see §6.1), so a corrupted frame is simply dropped.

7.3 Wi-Fi + MQTT client — components/wifi_mqtt_client/wifi_mqtt_client.cpp BSW

FunctionWhat it does

8. Wire Protocol & CRC16

Defined once in common/protocol_spec.h, compiled into both firmwares so the struct layout can never drift between them (both sides use #pragma pack(push, 1)).

Fig. 7 — uart_frame_t byte layout, exactly as declared in protocol_spec.h.

8.1 Handshake bytes

ConstantValueMeaning
PROTOCOL_SYNC_BYTE_10xAAFrame start marker 1
PROTOCOL_SYNC_BYTE_20x55Frame start marker 2
PROTOCOL_ACK_BYTE0x06ESP32 → STM32: frame accepted
PROTOCOL_NACK_BYTE0x15ESP32 → STM32: CRC mismatch

8.2 CRC16 (CCITT-FALSE)

calculate_crc16() is a static inline function in the shared header — same object code semantics compiled independently into both firmwares. Polynomial 0x1021, initial value 0xFFFF, MSB-first, no final XOR: 

uint16_t crc = 0xFFFF;
for each byte b:
    crc ^= (uint16_t)b << 8;
    repeat 8 times:
        crc = (crc & 0x8000) ? (crc << 1) ^ 0x1021 : (crc << 1);
return crc;

Fig. 8 — One full acquisition→publish cycle. Solid vertical arrows are sequencing within one MCU; diagonal dashed/accent arrows cross the UART/GPIO link between chips.

Timing values (10ms wake pulse, 100ms settle, 100000-iteration ACK timeout) are the literal constants in uart_handshake.c. The ACK timeout is a loop-iteration count, not a calibrated millisecond value — its real duration depends on CPU clock speed, so it's approximate by design (see the comment in uart_wait_for_byte()).

12. Engineering Notes: Bugs Found & Fixed

This tree started as a design skeleton with register operations written as comments rather than code. Getting it to actually compile surfaced a number of real, concrete bugs — recorded here since they're the kind of thing worth knowing before extending this codebase.

Both CMakeLists.txt files had duplicate, conflicting project()/add_executable() blocks

Both stm32_firmware/CMakeLists.txt and esp32_firmware/CMakeLists.txt contained an early legacy placeholder block (project(..._firmware) + add_executable(..._firmware main.c ...)) concatenated before the real build configuration. For STM32 this was a hard CMake error (duplicate target name). For ESP32 it was worse: the stray first project() call locked CMake's compiler detection onto the host's AppleClang before ESP-IDF's include($ENV{IDF_PATH}/tools/cmake/project.cmake) ever got a chance to set the xtensa cross-toolchain — producing a confusing downstream error deep in xtensa/project_include.cmake ("toolchain has not been set correctly") that looks unrelated to the actual root cause. Both files were rewritten to contain exactly one clean build definition.

STM32 driver/middleware/app files were pseudocode, not code

dma_adc.c, power_manager.c, uart_handshake.c, and main.c had function bodies consisting entirely of comments describing what register writes would happen ("// RCC->AHB2ENR |= ..."), with no actual code. Rewrote all four with real CMSIS register access against the real STM32L476 device header, plus added a linker script, startup file, SysTick delay driver, and pin-mapping header — none of which existed. See §6.

ESP-IDF v6 moved the mqtt component to the Component Registry

Core esp-idf no longer bundles the MQTT client — declaring REQUIRES mqtt now fails with "Failed to resolve component 'mqtt'". The fix is an idf_component.yml manifest pulling espressif/mqtt from the registry (not espressif/esp-mqtt, which doesn't exist — confirmed by hand against the registry API).

ESP-IDF v6 split the monolithic driver component

uart_receiver's CMakeLists.txt declared REQUIRES driver, which no longer transitively provides driver/uart.h/driver/gpio.h. Fixed by requiring esp_driver_uart and esp_driver_gpio directly, per the exact error message the real build produced.

-Werror=missing-field-initializers on partial designated initializers (C++ mode)

uart_config_t, wifi_config_t, and esp_mqtt_client_config_t were initialized with partial designated initializers (e.g. { .baud_rate = 115200, ... }), which is valid C and normally just a style warning — but GCC15 in this C++ build escalates it to a hard error, and newer ESP-IDF struct versions add fields (like uart_config_t::flags) that didn't exist when this code was originally written. Fixed by zero-initializing each struct with = {} first, then assigning the needed fields individually.

Implicit int→enum conversion (C vs. C++ semantics)

ESP_EVENT_ANY_ID is #define ESP_EVENT_ANY_ID -1 (a plain int). C freely converts that to esp_mqtt_event_id_t; C++ does not. Since wifi_mqtt_client.cpp is compiled as C++, this needed an explicit static_cast<esp_mqtt_event_id_t>(...).

7 duplicate legacy files caused a "two main() functions" situation

stm32_firmware/main.c, dma_adc.{c,h}, power_manager.{c,h}, and uart_handshake.{c,h} lived flat at the stm32_firmware/ root — an earlier, simpler, still-broken skeleton, never referenced by CMakeLists.txt's GLOB_RECURSE (which only globs app/src, drivers/src, middleware/src). They weren't a build error, but they were confusing dead weight — deleted outright rather than left as clutter.

14. Glossary

TermMeaning in this project
MCALMicrocontroller Abstraction Layer — direct register/peripheral access (drivers/).
BSWBasic Software / Service layer — protocol, framing, connectivity logic above MCAL (middleware/ and ESP32 components/).
DMA circular bufferA fixed-size SRAM buffer the DMA controller keeps rewriting from the start once it reaches the end, with zero CPU intervention (DMA_CCR_CIRC).
STOP2STM32L4's deepest RAM-retention low-power mode: core and most clocks off, SRAM and register state preserved, sub-µA class current draw.
CRC16 (CCITT-FALSE)16-bit cyclic redundancy check, polynomial 0x1021, init 0xFFFF, used to detect corrupted UART frames.
FreeRTOS queueThread-safe fixed-capacity ring buffer used here to hand telemetry_payload_t structs from uart_receiver_task to mqtt_publisher_task.
ESP-IDF componentESP-IDF's unit of modular code (its own CMakeLists.txt + REQUIRES/PRIV_REQUIRES list) — uart_receiver and wifi_mqtt_client are each one.
CMSISARM's Cortex Microcontroller Software Interface Standard — the vendor-neutral core headers (core_cm4.h etc.) plus ST's device-specific register header (stm32l476xx.h) this project's STM32 build depends on.
